# Search diagnostic capture and historical readiness outcomes

## Scope and decision

The bounded Search startup lane diagnoses two immutable historical application checkouts with the current candidate's probe. Its process status previously combined the original subject's readiness result with capture integrity. A faithfully captured historical 1000ms miss therefore failed the current diagnostic job even when the requested evidence was complete.

This dated change separates those two facts in the diagnostic runner only. It supersedes the process-exit interpretation in the earlier [profiling record](2026-10-05-search-startup-profiling.md); that record, original failed jobs, artifacts and source identities remain historical evidence. It does not fix a Search performance defect or change the current application's browser tests, readiness observer, 1000ms gate, repository CI, or protection rules. A current-product Search failure remains a real independent failure.

## Result contract

- `readiness`, including `onTime`, observer timestamps, start and deadline, is unchanged and persisted before late observation or cleanup.
- `outcome` and `failures` retain the original observed result, including `Original 1000ms initial-ready deadline failed`. A complete capture of a late subject still has `outcome: failure`.
- `captureOutcome` starts as `incomplete`. It becomes `captured` only after the original source-bound visit, readiness and sanitized observation persistence, required profile integrity checks, cleanup and final clean app/probe identity checks all succeed. `captureFailures` retains operational failures independently from the readiness miss and also keeps them visible in `failures`.
- `captureOutcome: captured` is necessary for diagnostic process exit code 0; incomplete or failed capture gives exit code 1. The CLI subsequently prints the summary and appends it to `GITHUB_STEP_SUMMARY` when configured. A summary-delivery write error still exits nonzero; `result.json` describes the already completed capture and does not record that later CLI delivery exception. There is no `continue-on-error`, retry, alternate ready selector, widened timeout or failure suppression.
- CPU/timeline truncation, missing or failed capture phases, backend data loss, coverage/privacy validation failure, source drift, observation errors, blocked non-local HTTP/WebSocket requests and teardown failure remain capture failures. Errors arriving during teardown are checked before success and retained in the sanitized observation.
- The GitHub step summary prints the historical application SHA, original readiness PASS/FAIL or NOT OBSERVED, observed elapsed/late timing when available, legacy observed outcome and separate capture result. It does not copy arbitrary error payloads into summary markup. Detailed evidence remains in the existing artifacts.

The fixed applications remain `7669713a853211bb36995039d3c16569799c3e88` for dark-1440 and `9e183f7a7d69e61d17d62d92e3ccdacd00196833` for light-390. Probe SHA binding, single visit, local-only routing, redaction, sampling interval and all budgets are unchanged. A historical subject failure is a diagnostic finding, and a capture success is not a current-product performance acceptance result.

## Independent-review repair CAPTURE-01

Independent review demonstrated that the inherited late-observation rejection handler treated an arbitrary protocol error as `ready: false`. The first dual-outcome candidate consequently reported capture success despite that operational error. The original +149ms miss remained intact, but the capture-success claim was wrong. The first frozen patch and executable negative evidence remain review history.

Late observation still uses one `waitForFunction` call with exactly 10000ms. Its elapsed wait is now measured with a monotonic clock after the progress write. Only an `Error` named `TimeoutError`, carrying the locked Playwright wait's explicit `page.waitForFunction: Timeout 10000ms exceeded.` message and an elapsed wait of at least 10000ms, counts as a completed non-ready observation. It is explicitly recorded as `lateObservation.outcome: timeout`, `ready: false`, with its sanitized error and elapsed time. A protocol error, unknown timeout or premature timeout becomes `outcome: error`, retains the sanitized error in `captureFailures` and the legacy failures, and exits nonzero. The runner still attempts the remaining profile/observation capture and every cleanup owner.

The new paired profiled/unprofiled runner controls failed 14/14 on the first candidate while its previous 65 cases passed. They cover ordinary/protocol rejection, immediate or 9999ms timeout, wrong-budget and unclassified timeouts, and the explicit full-budget non-ready outcome. Synthetic monotonic time isolates the contract without sleeping or changing the original readiness clock. The repaired probe suite passes 79/79. A separate local runner check also uses the installed, locked Playwright 1.58.2 `errors.TimeoutError` with the synthetic full-budget clock and passes. Neither check constitutes a real browser timeout observation.

Review also exercised the actual CLI summary/exit tail with a directory as `GITHUB_STEP_SUMMARY`. It printed the subject failure, then exited 1 on `EISDIR`. Its prior successful capture artifact remained successful. Summary delivery is deliberately a subsequent CLI action; no new result-file protocol is introduced to reclassify a completed capture when that delivery fails.
